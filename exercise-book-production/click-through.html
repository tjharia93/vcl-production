The rules this model follows

  • Covers, folds and inserts count in sets. A4 = 2 books per set, A5 = 3. One cover sheet + one fold set = one insert set. Only packing counts single books.
  • Covers: Material Receipt, cover sheets into Stores - VCL. Spoiled sheets are recorded but not added.
  • Folds: Material Receipt, fold sets into Stores - VCL (paper is taken out in Phase 2/3).
  • Inserts: Repack (no BOM). Out: covers × sets and folds × sets. In: inserts × sets. Blocked if either is short, because the site doesn't allow negative stock. There's no fold stock yet, so the first inserts need a fold count first, or the fold check held off.
  • Packing: Manufacture against the book's packing BOM. Books = full cartons × books per carton + loose books. Out: inserts (books + rejects ÷ up-count, rounded up to whole sets) and empty cartons. In: books into Finished Goods - VCL. Blocked if inserts or cartons are short.
  • Cartons (PC proposal, for your decision): one common carton per size and brand. How the page is built today

  • One script: five blocks for exercise books in front of the whole production-dev shell. Tabs switch with ?ebtab= (orders, comparison, finished, covers, cartons, inserts, packing); there is no hash routing.
  • Every call goes through /api/method/frappe.client.*; the generic resource API is never used. There are three copies of the API helpers and five of the escape function, and they don't all agree.
  • No confirmations: every write posts on one click. Messages show inline. No floor or touch mode.
  • Exports: ExcelJS for the orders workbook; jsPDF, autoTable and SheetJS for the comparison and aging.
  • Writes today: the inserts Repack and the cover Material Receipt. Packing is browser-only. Insert and submit aren't atomic, and stock is checked against a copy in the browser, so two users can race.
  • Orders Pending counts On Hold and Completed orders in its matrix, loads each Sales Order separately, and its patterns miss MNL/MGC, FNB and SQ13.

Safe deploy: scripts/deploy_eb_dev_page.py

  • Modelled on deploy_cp_traveller_v2.py. The source is the page files in git plus a deploy stamp (live modified time, hashes, git commit, who and when).
  • --check compares the live page with the repo: 0 = same, 1 = repo ahead, 2 = the live page has drifted.
  • Deploy refuses a dirty git tree, and refuses if the live page changed since the stamp. It saves with the page's modified, so a race is rejected, then re-reads and re-stamps.
  • --pull adopts a reviewed live edit. --force --reason is the only override, and it is logged.
  • The rule for every session: no direct REST edits of these Web Pages outside the script.
